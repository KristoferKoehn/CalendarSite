Fix the prefix redirects dropping the query string

Clicking the confirmation link landed on a page asking the reader to confirm the address they had
just confirmed. The page itself was fine — it redeems a `token` automatically. The token was never
arriving.

The fifteen redirect pages I added for the prefix move each redirected to a bare path:

    redirect("/calendar/verify-email")

So `/verify-email?token=…` became `/calendar/verify-email`, with the query discarded. The page then
saw no token and showed its "confirm your email" branch. Both emailed links were affected, since
both tokens are query parameters, along with the `next` parameter and any bookmarked filtered URL.

The fix is middleware rather than fifteen corrected pages. A page has to read `searchParams` to
forward the query, and this version of Next refuses to prerender a page that does without a Suspense
boundary — so the honest page-level fix is to give fifteen redirects a blocking-route declaration.
Middleware sees the whole URL, forwards the search string, and leaves the routes static.

308 rather than 307, because these are permanent and the destination is stable.

Also removes the fifteen page files, which middleware replaces, and the now-unused
tmp-fix-redirects generator.

Worth recording how this got through. I verified the redirects worked by checking that the old paths
returned 307s and that the destinations returned 200s — both of which were true while every query
string was being silently dropped. The check tested the status code and not the destination, and a
redirect's whole job is the destination.
