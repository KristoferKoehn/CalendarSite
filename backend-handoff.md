# Backend Hand-Off

## Purpose

This document is the contract between the CalendarSite frontend and the backend. The backend is written in a non-TypeScript, non-JavaScript language.

The frontend calls this contract through an HTTP client. The backend implements the contract without changing the frontend.

## Source of truth

| Artifact | What it is |
|---|---|
| `contract/out/openapi.json` | Machine-readable OpenAPI document. **Not committed** — git-ignored, generated by `npm run contract:generate`. |
| `contract/` | Zod schemas and OpenAPI path registrations that generate the document. |
| `api-contract.md` | Human-readable API surface and authorization model. |
| `project.md` | Original MVP spec (historical; predates the repo split). |

The OpenAPI document is the authoritative machine contract **once generated** — it
is not present in a fresh checkout. This file summarizes the parts the backend
must get exactly right.

> The implemented backend is the Go repo `CalendarBackend`. The cross-repo
> reference, including the audit of these documents, is
> `../documentation/unified-documentation.md`.

## Locked decisions

- Database: PostgreSQL.
- Bearer token lifetime: 24 hours.
- Nonexistent and ambiguous DST times return `INVALID_INPUT`.
- Admin is a role on a normal user. URLs do not contain an `/admin/` prefix.
- Resources are created by admins.
- The frontend stores the token and calls the backend directly over HTTP.
- `from` and `to` on `GET /appointments` are calendar dates in America/Los_Angeles.
- Frontend serves on `http://127.0.0.1:3000` locally; deployed at `https://couchcollective.software`.
- Backend binds `127.0.0.1:4001` **by default for local development**; the deployed
  backend is reachable at `https://couchcollective.software:4000`. These are not in
  conflict — deployments set `PORT=4000` (or proxy 4000 to the local listener).

## API surface

Authorization values: `public`, `user`, `admin`, or `owner or admin`.

`GET /healthz` (public) returns `200 {"status":"ok"}`. `POST /mcp` speaks JSON-RPC
2.0. Neither is registered in the generated OpenAPI document.

### Auth

| Method | Path | Access | Request | Response |
|---|---|---|---|---|
| POST | `/auth/register` | public | `{ "email": string, "password": string }` | `201` `{ "userId": string }` |
| POST | `/auth/login` | public | `{ "email": string, "password": string }` | `200` `{ "token": string, "expiresAt": string }` |
| GET | `/auth/me` | user | none | `200` `User` |
| DELETE | `/auth/me` | user | none | `200` `User` (the deleted user) |

`register` returns only `userId`. The frontend then calls `login` itself.

`DELETE /auth/me` lets any authenticated user remove their own account. Their
appointments are left in place. `409 CONFLICT` if they are the last admin.

### Resources

| Method | Path | Access | Request | Response |
|---|---|---|---|---|
| GET | `/resources` | user | none | `200` `{ "resources": Resource[] }` |
| POST | `/resources` | admin | `{ "name": string, "description"?: string, "timezone"?: string }` | `201` `Resource` |
| PATCH | `/resources/{id}` | admin | partial of the create body | `200` `Resource` |
| DELETE | `/resources/{id}` | admin | none | `200` `Resource` (deactivated) |

`DELETE` deactivates by setting `active` to `false`. It does not delete the row.

### Users

| Method | Path | Access | Request | Response |
|---|---|---|---|---|
| GET | `/users` | user | none | `200` `{ "users": User[] }` |
| GET | `/users/{id}` | user | none | `200` `User` |
| PATCH | `/users/{id}` | admin | `{ "role"?: "user" \| "admin", "isAgent"?: boolean }` | `200` `User` |
| DELETE | `/users/{id}` | admin | none | `200` `User` |

At least one of `role` or `isAgent` is required on `PATCH`.

**Profiles are a shared directory.** Any authenticated user may list every user and
read any single profile. Only `role` and `isAgent` changes remain admin-only.

`DELETE` removes the user row and **leaves the user's appointments in place**. It returns `409 CONFLICT` when the target is the caller or is the last remaining admin. It no longer conflicts on "user has appointments" — clear those with `DELETE /appointments/{id}`. A non-admin deleting themselves uses `DELETE /auth/me` instead.

### Own profile

| Method | Path | Access | Request | Response |
|---|---|---|---|---|
| PATCH | `/auth/me` | user | profile fields, see below | `200` `User` |

Takes no user id, so editing somebody else's profile is impossible. Fields omitted
from the body are left alone; sending `null` clears one. It cannot change `email`,
`role`, or `isAgent`.

```json
{
  "displayName": "string | null, max 100",
  "birthMonth": "integer 1-12 or null",
  "birthDay": "integer 1-31 or null",
  "pronouns": "string | null, max 50",
  "jobTitle": "string | null, max 100",
  "bio": "string | null, max 500"
}
```

`birthMonth` and `birthDay` are supplied **together** or not at all, and clearing
both is done by sending both as `null`. There is deliberately no birth year.

### Appointments

| Method | Path | Access | Request | Response |
|---|---|---|---|---|
| POST | `/appointments` | user | `{ "resourceId": string, "title": string, "description"?: string, "date": string, "startTime": string, "endTime": string }` | `201` `Appointment` |
| GET | `/appointments` | user | query: `resourceId?`, `userId?`, `title?`, `from?`, `to?`, `status?` | `200` `{ "appointments": Appointment[] }` |
| POST | `/appointments/{id}/cancel` | owner or admin | none | `200` `Appointment` |
| POST | `/appointments/{id}/reschedule` | owner or admin | `{ "title": string, "description"?: string, "date": string, "startTime": string, "endTime": string }` | `200` `Appointment` |
| DELETE | `/appointments/{id}` | admin | none | `200` `{ "status": "deleted", "id": string }` |

`DELETE /appointments/{id}` is a hard delete and is admin-only. It is how
appointments belonging to a deleted account are cleared.

## Object shapes

### User

```json
{
  "id": "uuid",
  "email": "string",
  "displayName": "string | null",
  "birthMonth": "integer 1-12 | null",
  "birthDay": "integer 1-31 | null",
  "pronouns": "string | null",
  "jobTitle": "string | null",
  "bio": "string | null",
  "role": "user | admin",
  "isAgent": false,
  "createdAt": "ISO UTC"
}
```

The profile fields are always present and nullable. `displayName` is the human label
to show; fall back to `email` when it is null. `birthMonth` and `birthDay` are
always both set or both null.

### Resource

```json
{
  "id": "uuid",
  "name": "string",
  "description": "string | null",
  "timezone": "America/Los_Angeles",
  "active": true,
  "createdAt": "ISO UTC"
}
```

`description` is nullable, not optional, in responses.

### Appointment

```json
{
  "id": "uuid",
  "userId": "uuid",
  "ownerEmail": "string",
  "ownerName": "string | null",
  "resourceId": "uuid",
  "title": "string",
  "description": "string",
  "startAt": "ISO UTC",
  "endAt": "ISO UTC",
  "startAtLocal": "Seattle ISO with offset",
  "endAtLocal": "Seattle ISO with offset",
  "status": "booked | cancelled",
  "createdAt": "ISO UTC",
  "updatedAt": "ISO UTC",
  "cancelledAt": "ISO UTC | null"
}
```

`ownerEmail` is the owner's email, captured when the appointment was created. It is
required and always present. It exists so an appointment stays meaningful after its
owner's account is deleted, at which point `userId` is a historical reference that
may match no user — treat `userId` as *possibly dangling* and `ownerEmail` as the
reliable label.

`ownerName` is the owner's display name **at the time of booking**, or null if they
had not set one. To render an owner, use `ownerName` and fall back to `ownerEmail`
when it is null. Both live on the appointment, so the label still resolves for a
deleted owner; do not look the owner up by `userId`.

## Deleting users and appointments

- `DELETE /users/{id}` (admin) **hard-deletes the account and leaves its
  appointments in place.** It no longer conflicts on "user has appointments".
- It still returns `409` when the target is the caller or the last remaining admin.
- A non-admin cannot delete another user (`403`); they delete *themselves* with
  `DELETE /auth/me`.
- To clear the appointments left behind, an admin calls
  `DELETE /appointments/{id}`.

## Response shapes

- Collections return `{ "<plural>": [...] }`.
- Single resources return the object directly.
- Errors always use the envelope below.

## Error contract

```json
{
  "error": {
    "code": "CONFLICT",
    "message": "Overlapping booking",
    "details": {}
  }
}
```

`details` is optional and may be omitted.

| Code | HTTP status | Used for |
|---|---|---|
| `INVALID_INPUT` | 400 | schema violations, nonexistent or ambiguous DST times, `endTime <= startTime` |
| `UNAUTHENTICATED` | 401 | missing or expired token, wrong email or password |
| `FORBIDDEN` | 403 | wrong role or not the owner |
| `NOT_FOUND` | 404 | missing user, resource, or appointment, or inactive resource |
| `CONFLICT` | 409 | overlapping booking, duplicate email, already cancelled, delete self / last admin |
| `INTERNAL` | 500 | unexpected errors |

## Authentication

- Requests send `Authorization: Bearer <token>`.
- Tokens are opaque, expire after 24 hours, and are stored hashed in the `sessions` table.
- Passwords use `argon2id` or `bcrypt`. Plaintext is never stored or logged.
- Email is normalized with trim and lowercase before storage and comparison.
- Password minimum length is 8.

## Datetime contract

Input is a date plus two wall-clock times in `America/Los_Angeles`:

```json
{
  "date": "2026-10-10",
  "startTime": "14:00",
  "endTime": "15:00"
}
```

Rules:

- Store as `TIMESTAMPTZ` in UTC.
- `endTime` must be strictly after `startTime`.
- Spring-forward nonexistent times return `INVALID_INPUT`.
- Fall-back ambiguous times return `INVALID_INPUT`.
- `startAt` and `endAt` are UTC ISO strings with `Z`.
- `startAtLocal` and `endAtLocal` are ISO strings with the Seattle offset, for example `2026-10-10T14:00:00-07:00`.
- The overlap interval is half-open: `[startAt, endAt)`.

## Data model

See `project.md` section 4. The required tables are `users`, `resources`, `appointments`, and `sessions`.

The overlap invariant must be enforced at the database level with the PostgreSQL exclusion constraint in `project.md` section 4. Cancelled appointments do not block overlaps.

## Business rules

- Appointments are readable by **every authenticated user**. `GET /appointments` is
  not scoped to the caller, and any caller may filter by any `userId`. Read access is
  shared; write access is not — only the owner or an admin may cancel or reschedule.
- `title` is required (1-200 characters). `description` is optional (max 2000 characters); an empty string means none.
- `GET /appointments?title=...` filters by case-insensitive substring, with `%` and `_` treated as literal characters.
- Cancel and reschedule accept the appointment owner or an admin.
- Reschedule validates the same way as create, updates title/description, and the overlap check excludes the appointment being rescheduled.
- Admin endpoints return `FORBIDDEN` for non-admins.

## MCP over HTTP

`POST /mcp` is backend-only. The frontend does not call it. It is implemented in
the Go backend against `project.md` section 8 using the same core services:

- Stateless JSON-RPC 2.0 over `POST`. Only `POST` is accepted. There is **no**
  session-id header; the "Streamable HTTP" session pattern was not implemented.
- Methods: `initialize` (advertises protocol version `2024-11-05`), `tools/list`,
  `tools/call`, and `ping`.
- Tools, exactly eight: `auth.register` and `auth.login` (public), plus
  `resources.list`, `appointments.create`, `appointments.cancel`,
  `appointments.reschedule`, `appointments.list`, and `appointments.delete`
  (bearer auth; `appointments.delete` is admin-only).
- Contract errors map to JSON-RPC error code `-32000` with the contract code in
  `error.data.code`.

## Dev seed parity

Seed the backend with these values for a frictionless first connection:

- `admin@example.com` / `password123`, role `admin`.
- `user@example.com` / `password123`, role `user`.
- `Room A`, `Room B`, both active, timezone `America/Los_Angeles`.

## Ports and origins

- Frontend dev: `http://127.0.0.1:3000` (loopback only, as configured in `package.json`).
- Backend REST and MCP, local default: `http://127.0.0.1:4001`. MCP is `POST /mcp` on the same listener; `GET /healthz` is an unauthenticated liveness probe.
- Backend REST and MCP, **deployed**: `https://couchcollective.software:4000`. This is the port the hosted frontend calls, and `GET /healthz` there returns `200 {"status":"ok"}`. Port 4001 is not reachable from outside.
- The frontend points at the backend with `NEXT_PUBLIC_API_URL`. There is no default and no `.env.example`; a missing value is not detected at startup but makes every request fail with `INTERNAL`.

## CORS

The backend default allowlist is **`https://couchcollective.software` only**
(`internal/config/config.go`). It is extended with the comma-separated
`CORS_ORIGINS` environment variable.

> An earlier revision of this document listed a four-entry allowlist —
> `http://localhost:3000`, `http://127.0.0.1:3000`, `http://couchcollective.software`,
> `http://192.168.1.169`. That is **no longer the default**; local origins were
> removed. Set `CORS_ORIGINS` explicitly to call the API from a local dev server.

Note that the CORS layer only sets headers for allowed origins and short-circuits
`OPTIONS` with `204`; it does not reject other origins. Non-browser clients such as
MCP agents ignore CORS entirely.
